# 03: 潛行模式、內建切換條件與復原模式

**What to build:** 新增潛行模式（使用者故事 1～20、30、33），以及復原模式的記錄、程式啟動時的復原（28），和虛擬螢幕意外消失時的處理（29）。核心新增「虛擬螢幕」介面，Windows 轉接層以 SudoVDA 的 IOCTL 實作（做法依票 02 的結果）；偵測螢幕時排除本程式建立的虛擬螢幕。驅動的安裝與移除已在票 02 完成。

**Blocked by:** 01, 02

**Status:** 實作完成，待手動實測（2026-11-22）

- [x] 模式分頁有「新增潛行模式（虛擬螢幕）」；複製潛行模式得到潛行模式；一般模式和潛行模式不能互相轉換；清單上看得出哪些是潛行模式
- [x] 潛行模式的設定：名稱、圖示顏色、手動切換進入時的自動切換、虛擬螢幕解析度與更新率（下拉選單，預設 1920×1080@60）；不顯示「未記錄的螢幕」。下拉選單從驅動實際提供的模式中挑常見的（3840×2160、2560×1440、1920×1080、1366×768、1280×720 等），更新率依解析度列出（見票 02 的 Answer）

- [x] 內建切換條件的目標失效時，改成順序第一個一般模式，並在套用時提示
- [x] 內建切換條件一律只認實體鍵盤滑鼠，不受「忽略遠端連線軟體送出的鍵盤滑鼠輸入」影響

- [x] 進入潛行模式時，等的是虛擬螢幕**存在**，不是它被開啟：Windows 可能一建立就依記憶套用上次的配置（已經只開虛擬螢幕，或讓虛擬螢幕維持關閉），兩種情況都明確套用「只開虛擬螢幕」
- [x] 只在進入潛行模式時建立虛擬螢幕，其他時候都不建立（Windows 可能依記憶直接關掉實體螢幕）
- [x] 更新率比對時把 59 和 60 視為相同：指定 60 Hz 建立會得到 59.94 Hz（GDI 回報 59），不要因此判定失敗或一直重新套用
- [x] 驅動不可用或建立失敗時，拒絕切換並通知，維持原本的模式
- [x] 驅動不可用時，模式分頁中潛行模式旁顯示警告與「安裝驅動」按鈕（原票 05，使用者故事 34）
- [x] 處於潛行模式時，從介面執行緒持續送心跳（每秒一次就夠），一直送到虛擬螢幕移除為止，離開潛行模式、套用一般模式的期間也要送；不在套用螢幕設定的執行緒送（`SetDisplayConfig` 可能花 1～2 秒）。移除時驅動回報找不到，就當成已經被移除

- [x] 虛擬螢幕意外消失時，切回復原模式並通知
- [x] 偵測、擷取、套用、畫布都排除本程式建立的虛擬螢幕，其他虛擬顯示照舊。以介面卡的硬體 ID `Root\SudoMaker\SudoVDA` 辨識，不用目標 ID（每次建立都會變）
- [x] cfg：`RestoreMode`、`Kind`、`VirtualWidth`／`VirtualHeight`／`VirtualRefreshRate`、`BuiltIn`，加上註解；讀取時驗證內建切換條件，不符就修正並提示
- [x] 各分頁的說明與右鍵選單的說明，補上潛行模式、內建切換條件與復原模式；潛行模式的說明要寫出效果與用途（使用者故事 8a）：遠端連線、省下螢幕的電與部分顯示卡負擔（不及睡眠），以及「潛行」不是防窺

## Comments

### 2026-11-22 依票 02 的實測結果修改

- 票 02 的精靈實測沒有推翻 spec 的假設：驅動能用程式的介面安裝與移除；一般使用者權限就能建立虛擬螢幕；心跳停止後 3.4～3.9 秒內移除；Chrome 遠端桌面看得到只剩虛擬螢幕的畫面，送來的輸入全部帶注入旗標；睡眠喚醒後虛擬螢幕還在。詳見票 02 的 Answer。
- 新發現：Windows 的顯示資料庫會依「接上了哪些螢幕」記住上一次的配置（`SDC_SAVE_TO_DATABASE`），包括含虛擬螢幕的組合。所以虛擬螢幕一建立，Windows 就可能自己改配置。
- 依此修改的驗收項目：
  - 解析度下拉選單：從驅動實際提供的模式中挑選。
  - 進入潛行模式：等虛擬螢幕存在就好，不論 Windows 有沒有開啟它，都明確套用「只開虛擬螢幕」。
  - 只在進入潛行模式時建立虛擬螢幕（新增一項）。
  - 更新率 59／60 視為相同（新增一項）。
  - 心跳：送到虛擬螢幕移除為止，移除時「找不到」當成已移除。
  - 偵測：以介面卡的硬體 ID 排除虛擬螢幕。
  - 手動實測：用手機再看一次「調整桌面大小以符合」。

### 2026-11-22 實作完成（待手動實測）

#### 核心

- `Ports.cs`：
  - 新增 `IVirtualDisplay`：`Create`、`Remove`、`Ping`、`Exists`。
  - `IMonitorSystem.BeginApply` 多一個 `VideoMode? virtualMode`：不為 null 時是潛行模式，只開虛擬螢幕並設為這個解析度。
  - `IUsageSignals.TakeHookUsage` 改回傳 `HookUsage(Any, Physical)`。`InputHookPolicy` 拿掉 `IgnoreRemoteInput`，改由核心依切換條件選用：內建切換條件一律只看 `Physical`。
- 模式：
  - `ModeConfig.Kind`（`Normal`／`Remote`）建立後不能改；`VirtualMode` 預設 1920×1080@60。
  - `VirtualDisplayModes.Common` 是下拉選單的常見模式，取自票 02 的 55 個模式。
  - `VirtualDisplayModes.SameRefreshRate` 把 59 和 60 視為相同。
- 內建切換條件 `SwitchCondition.BuiltIn`，相關的操作都在 `AppConfig`：
  - `AddRemoteMode`、`DuplicateMode`：加在清單最後。
  - `RemoveMode`：一起刪除；目標是被刪除的模式時，改成第一個一般模式。
  - `SwitchConditionRemovalBlocker`：不能刪除。
  - `Validate`：每個潛行模式剛好一條、條件鎖定、目標是一般模式。
  - `RepairBuiltInConditions`：讀取 cfg 時修正，並在啟動通知中提示。
  - 套用設定時，目標因刪除模式而改變的，`ApplySettings` 跳通知說明。
- 復原模式：
  - `AppConfig.RestoreModeId` 在切換到一般模式、擷取時更新，重新編號時跟著改。
  - `RestoreTarget()` 在復原模式不存在時用第一個一般模式。
  - `ApplyPlanner.AllOn`：沒有一般模式，或規劃被拒絕時，開啟所有接上的螢幕。
- 協調者的流程：
  - 進入潛行模式：
    1. `Create`。驅動不可用或建立失敗時，拒絕切換並通知。
    2. 套用「所有螢幕關閉＋只開虛擬螢幕」。
    3. 套用失敗時移除虛擬螢幕、等一下，再重新套用原本的模式。
  - 潛行模式之間：不重新建立，只換解析度。
  - 離開潛行模式：
    1. 依一般模式開啟螢幕（虛擬螢幕還在）。
    2. `Remove`，等 1.5 秒讓 Windows 依記憶改完配置。
    3. 重新套用一次一般模式。
  - 目標模式的規劃被拒絕時（例如記錄的螢幕都沒接上），改為開啟所有接上的螢幕。否則坐在電腦前的人會困在全暗的潛行模式裡。
  - 心跳：每次 `Tick` 都送，從建立一直送到移除。
  - 程式啟動時：
    - 先移除上次留下的虛擬螢幕（若還在）。
    - 目前模式是潛行模式時，改套用復原模式。
  - 一致性檢查（`Tick`，緩衝期之後）：
    - 處於潛行模式但虛擬螢幕不見了：等 1.5 秒後切回復原模式，並通知（不受「自動切換時跳出通知」影響），不重建。
    - 查詢失敗不當成消失。
    - 目前模式不是潛行模式卻留著虛擬螢幕（例如重新載入 cfg 後）：重新套用目前模式。
  - 擷取：處於潛行模式時 `CaptureBlocker` 擋下工作列與設定視窗的擷取，預覽套用也擋下。
- cfg 新增以下欄位，並加上註解：
  - `[General] RestoreMode`
  - `[Mode.N] Kind`、`VirtualWidth`／`VirtualHeight`／`VirtualRefreshRate`（潛行模式不寫 `UnlistedMonitors` 與螢幕設定，讀取時忽略）
  - `[Switch.N] BuiltIn=1`
- 沒有一般模式的 cfg：讀取時以目前螢幕狀態補上「預設」模式。內建切換條件與復原模式都需要一般模式。

#### Windows 轉接層

- `SudoVdaVirtualDisplay`：
  - IOCTL 的寫法同 VddProbe，但用新的 GUID。
  - 移除時，驅動回報找不到（1168）當成已移除。
- `WindowsMonitorSystem`：
  - 以介面卡的硬體 ID `Root\SudoMaker\SudoVDA` 排除虛擬螢幕（以 LUID 快取），偵測、擷取、套用、畫布都看不到它。
  - `ApplyVirtualOnly`：
    1. 等虛擬螢幕存在（最多 5 秒）。
    2. 只開它。
    3. 解析度或更新率不同時才設定（59／60 視為相同）。
  - 套用一般模式失敗時的還原：原本開著的虛擬螢幕也重新開啟。
- `WindowsUsageSignals`：分別記錄全部輸入與實體輸入。
  - 滑鼠的位移分開累加：注入的移動也會改變游標位置。
  - Windows 遠端桌面工作階段的輸入不算實體輸入。

#### 介面

- 模式分頁：
  - 「新增潛行模式（虛擬螢幕）」；清單標示「（潛行）」。
  - 潛行模式顯示虛擬螢幕的解析度與更新率下拉選單，以及效果與用途的說明（使用者故事 8a）。
  - 驅動不是「已安裝」時，顯示紅字警告與「安裝驅動」。安裝與移除抽成 `DriverController`，一般設定分頁共用。
  - 處於潛行模式時，擷取按鈕停用並說明原因。
  - 刪除模式時，對話框列出目標會被改掉的內建切換條件。
- 切換條件分頁：
  - 內建切換條件的來源顯示「（內建）」。
  - 條件、使用來源、強制鎖定（灰底）；目標下拉選單只列一般模式。
  - 「刪除」停用，按下也會說明原因。
- 螢幕配置分頁：選到潛行模式時以說明取代畫布，預覽停用。
- 右鍵選單：
  - 目前模式與模式清單標示潛行。
  - 處於潛行模式時，擷取項目變成「無法擷取：處於潛行模式（所有螢幕都關閉）」並停用。
- 各分頁與右鍵選單的說明都補上潛行模式、內建切換條件與復原模式。

#### 與票不同的地方

- **心跳另有補送的執行緒。** 票上寫「從介面執行緒持續送心跳…不在套用螢幕設定的執行緒送」，但實測（見下方）SetDisplayConfig 開關實體螢幕時，介面執行緒的訊息處理也卡住 2.5～2.8 秒，加上每秒一次的間隔就超過驅動的 3 秒。結果虛擬螢幕在離開潛行模式的套用途中被驅動移除；進入時若遇到同樣情況就會失敗。
  - 現在：協調者照樣每秒從介面執行緒呼叫 `Ping`。轉接層另有心跳執行緒每 0.5 秒補送，但只在介面執行緒 5 秒內送過時才補。
  - 介面短暫卡住不會讓虛擬螢幕消失；介面真的卡死時，心跳最多 5 秒後停止，再過 3 秒驅動移除虛擬螢幕。
  - spec 的對應句子已更新。票 04 的守護程式監看心跳時要考慮這 5 秒。
- **離開潛行模式時多套用一次。** 移除虛擬螢幕後，Windows 會依記憶套用「只有實體螢幕」時的配置（票 02），可能不是剛套用的一般模式。所以等 1.5 秒再重新套用一次；沒有變化時幾乎不花時間。
- **範圍外但順手做的。**
  - 啟動時移除上次留下的虛擬螢幕。
  - 「目前不是潛行模式卻留著虛擬螢幕」的一致性處理。
  - 沒有一般模式的 cfg 補上「預設」模式。
- 程式結束時（右鍵選單「關閉程式」）只停止心跳，約 3 秒後驅動移除虛擬螢幕、Windows 點亮實體螢幕。先切回復原模式是票 04 的範圍。

#### 手動實測的步驟

1. 從工作列關閉正在執行的程式，執行 `build.bat`，啟動 `release/AutoDisplayMode.exe`。
2. 在設定視窗新增潛行模式，確認：
   - 解析度下拉選單。
   - 切換條件分頁的內建切換條件（目標選平常用的一般模式）。
   - 螢幕配置分頁的說明。
3. 從右鍵選單切到潛行模式：實體螢幕全暗。
   - 用 Chrome 遠端桌面連線，看得到畫面、可以操作。
   - 遠端操作不會離開潛行模式。
4. 在遠端從右鍵選單切到另一個潛行模式（不同解析度）：只換解析度。
5. 回到電腦前動一下滑鼠：回到內建切換條件的目標模式，螢幕配置正確。
6. 移除驅動（或暫時改 cfg 讓驅動找不到）後切到潛行模式：被拒絕、跳通知、留在原本的模式；模式分頁的潛行模式旁有警告與「安裝驅動」。
7. 用比例跟電腦不同的裝置（例如手機）連線，記錄「調整桌面大小以符合」的行為：解析度有沒有改變、離開潛行模式後是否正常。
8. 處於潛行模式時關閉程式再開啟：啟動時改套用復原模式。
