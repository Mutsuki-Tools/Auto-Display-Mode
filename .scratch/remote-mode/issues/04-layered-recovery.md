# 04: 分層復原，以及目標模式「回到上個配置」

**Blocked by:** 03

**Status:** 完成（2026-11-22 手動實測通過）

這張票有兩個互不相依的部分，可以分開做、分開提交：

- **第一部分：分層復原**（ADR-0006，使用者故事 24～27）：處於潛行模式時，不論程式怎麼結束，都要當下切回復原模式。
- **第二部分：「回到上個配置」**（使用者提出）：切換條件的目標模式可以選「回到上個配置」，切回進入目前模式之前所在的模式。

## 開工前要知道（票 02、03 的結果）

**已經做好的（票 03）**

- 協調者的 `Start()` 會移除上次留下的虛擬螢幕，目前模式是潛行模式時改套用復原模式。斷電後重開機的復原已經完成。
- 虛擬螢幕意外消失時，會切回復原模式並通知。
- 離開潛行模式的順序（守護程式可以沿用）：
  1. 依一般模式開啟螢幕（虛擬螢幕還在）。
  2. 移除虛擬螢幕。
  3. 等 1.5 秒（`AppCoordinator.SettleMs`）。
  4. 重新套用一次。
- `TrayApp.ExitApp` 目前只停止心跳，還沒先切回復原模式。

**心跳**

- SetDisplayConfig 開關實體螢幕時，介面執行緒會卡住 2.5～2.8 秒，超過驅動的 3 秒逾時。
- 所以 `SudoVdaVirtualDisplay` 另有心跳執行緒，每 0.5 秒補送，但只在介面執行緒 5 秒內呼叫過 `Ping` 時才補。介面真的卡死時，最多約 8 秒虛擬螢幕才會消失。
- 守護程式判斷「心跳逾時」時，也要容許介面短暫卡住幾秒。

**Windows 自己的還原（票 02 實測，只驗證過單螢幕）**

- 只剩虛擬螢幕時強制結束程式：3.4 秒後驅動移除虛擬螢幕，再過約 0.4 秒，Windows 以它記住的「只有實體螢幕」配置點亮螢幕，沒有黑畫面。
- Windows 還原的是實體螢幕單獨接著時最後存下的配置（現有程式套用時用 `SDC_SAVE_TO_DATABASE`），通常就是復原模式。但多螢幕沒有驗證過，而且 cfg 的目前模式需要有人更新，所以守護程式仍然需要。

**其他**

- 「調整桌面大小以符合」：用手機連線時沒有任何改變，使用者決定不需要。虛擬螢幕的解析度照模式的靜態設定，本票不必處理。

## 第一部分：分層復原

### 程式自己結束時

- [x] 從右鍵選單結束程式時，若處於潛行模式，先套用復原模式（等它完成）再結束
- [x] 收到 `WM_QUERYENDSESSION`／`WM_ENDSESSION`（關機、登出、重開機）時，若處於潛行模式，先套用復原模式

### 守護程式

- [x] 用同一個 exe 加參數啟動，不放進主程式的 job object；進入潛行模式時啟動，經由切換離開潛行模式時結束
- [x] 監看主程式的存活與心跳（逾時要容許介面卡住幾秒，見上方「心跳」）
- [x] 主程式不是正常結束或心跳逾時時，依序：
  1. 讀取 cfg。
  2. 移除虛擬螢幕（若還在）。
  3. 等 Windows 自己的還原結束（約 0.4 秒；可以等螢幕配置不再變化），避免和 Windows 同時改配置。
  4. 套用復原模式。
  5. 更新 cfg 的目前模式，然後結束。
- [x] 主程式正常結束時通知守護程式，不會重複套用
- [x] 守護程式套用後，主程式若從卡住中恢復，不會又切回潛行模式（依票 03「虛擬螢幕意外消失」的處理，以及 cfg 的目前模式）
- [x] 只能有一個守護程式；主程式重新啟動時，若守護程式還在，要能正確接手或結束它

### 測試與實測

- [x] 測試：核心中能測的部分（例如結束前的復原、守護程式的決策邏輯，若有抽出）
- [x] 手動實測，每種都要在幾秒內回到復原模式：
  - 用工作管理員結束主程式
  - 讓主程式卡住（例如以除錯器暫停）
  - 登出
  - 重開機
- [x] 手動實測：結束守護程式本身時，由驅動的心跳保險與 Windows 接手
- [x] 手動實測要包括平常使用的多螢幕一般模式：主程式與守護程式都被強制結束後，記錄 Windows 自己還原成什麼樣子

## 第二部分：目標模式「回到上個配置」

### 已決定的事

- **意思是「上一個一般模式」**：最近一次所在、而且不是目前模式的一般模式（使用者確認了「而且不是目前模式」這個解讀）。處於潛行模式時就是復原模式；處於一般模式時是在它之前所在的一般模式，中間經過的潛行模式不算。
- **名稱**：介面上的選項叫「回到上個配置」（使用者決定：直白、沒有專有名詞）。GLOSSARY 把「配置」列為「模式」要避免的說法，所以「配置」只用在這個選項的文字，程式、cfg、說明的內文都稱為「上一個一般模式」。
- **記錄方式**：復原模式換成另一個一般模式時，原本的復原模式記為「復原模式之前的一般模式」，存進 cfg，重新啟動後仍記得。重新套用同一個模式不算。
- **實際目標在切換時才決定**：
  - 由復原模式與復原模式之前的一般模式算出，所以上一個一般模式不會是潛行模式。
  - 不存在（被刪除、還沒切換過）時，用順序第一個一般模式；那就是目前模式時不切換。
  - 規劃被拒絕時比照票 03：離開潛行模式時開啟所有接上的螢幕，其他情況拒絕切換。
- **內建切換條件的預設目標**：新建或複製潛行模式時，預設改成「回到上個配置」（使用者決定，取代使用者故事 15 的「順序第一個一般模式」）。已經存在的不自動改。
- **不會失效**：cfg 寫成 `To=Previous`，不指向模式編號，重新編號與刪除模式都不影響它。內建切換條件「目標失效時改成第一個一般模式」的規則照舊，但不會發生在這個選項上。

### 2026-11-22 第一部分完成

- **做法**：
  - 協調者新增 `PrepareExit()`／`ReadyToExit`：結束前處於潛行模式（或還有虛擬螢幕）就切回復原模式，只試一次；失敗時照樣結束。右鍵選單「關閉程式」與 `WM_ENDSESSION` 都走這條路；後者在視窗程序裡以巢狀訊息迴圈等完成（最多 20 秒），`WM_QUERYENDSESSION` 時登記關機畫面顯示的原因。
  - 守護程式（`Windows/RecoveryGuardian.cs`）是同一個 exe 加 `--guardian`，在 `Program.Main` 拿 mutex 之前處理。主程式先啟動中繼程序 `--guardian-launch`（盡量 `CREATE_BREAKAWAY_FROM_JOB`），由它啟動守護程式後結束，所以守護程式不是主程式的子程序，工作管理員的「結束工作」不會一起結束它。
  - 兩邊以具名共用記憶體溝通：心跳時間（`QueryUnbiasedInterruptTime`，不含睡眠）、守護的代數（0 表示不需要）、「已接手」。心跳 6 秒沒更新就判斷卡住。代數不同的守護程式自己結束；具名 mutex 讓同時只有一個在守護，主程式啟動時也等正在復原的守護程式結束再讀 cfg。
  - 守護程式接手時用自己的協調者（`AppCoordinator.TakeOver`）：移除虛擬螢幕、等 1.5 秒、套用復原模式、更新 cfg 的目前模式，通知後結束。
  - 主程式從卡住中恢復時，看到守護程式「接手中」就不再送心跳，也不能手動切換，等它「完成」（最多 60 秒）再切回復原模式，並通知「有一段時間沒有回應」。這樣兩個程序不會同時改配置與 cfg。
  - 協調者新增 `IRecoveryGuard` 介面（Arm／Disarm／Beat／TakeOver），建立虛擬螢幕後啟動守護，虛擬螢幕移除或消失時結束守護。守護程式的判斷（守護狀態、主程式存活、心跳逾時）抽成核心的 `GuardianRules.Decide`，有測試。
  - 主程式啟動時最多等 70 秒，讓正在復原的守護程式先完成（守護程式復原的上限是 60 秒）。
- **實測**（拋棄式程式，用真正的協調者、守護程式與 SudoVDA；三台螢幕的一般模式）：
  - 正常結束：先切回復原模式再結束，守護程式跟著結束。從開始結束到完成約 12 秒，多半花在三台螢幕的套用（沿用票 03 離開潛行模式的順序）。
  - 強制結束主程式（`Process.Kill`，與工作管理員相同）：守護程式約 1 秒內移除虛擬螢幕，Windows 隨即點亮螢幕；之後套用復原模式、cfg 改回，守護程式結束。
  - 主程式的介面執行緒卡住 30 秒：卡住後約 6 秒守護程式接手，螢幕在 12 秒內全亮，第 17 秒 cfg 改回復原模式。主程式醒來後切回復原模式，並跳出「有一段時間沒有回應」的通知。
  - 卡住 10 秒（主程式醒來時守護程式還在套用）：主程式等了 8 秒，守護程式完成後才自己切回。
  - 主程式與守護程式都被強制結束：約 9 秒內 Windows 自己點亮三台螢幕，解析度與更新率都和一般模式相同（2560×1600@60、3840×2160@160、2560×1440@170）。cfg 仍是潛行模式，下次啟動時改套用復原模式。
  - 守護程式的父程序是已結束的中繼程序。
- **還沒實測（要請使用者做）**：
  - 用工作管理員結束主程式（release 版）。
  - 以除錯器暫停主程式。
  - 登出、重開機：`WM_ENDSESSION` 時能不能改螢幕配置，以及約 12 秒的套用會不會被 Windows 中斷。
- **已知限制**（審查時提出，暫不處理）：
  - 不允許脫離 job object 時，守護程式照常啟動、留在主程式的 job 裡（從檔案總管或開機啟動時沒有 job）。
  - 主程式在守護程式開啟共用記憶體之前就閃退時，守護程式直接結束，由第 3 層接手。
  - 主程式卡在切換途中、守護程式接手後，主程式恢復時完成那次切換，會把 cfg 的目前模式寫回一次，下一秒再切回復原模式修正。

### 2026-11-22 第二部分完成

- **依新定義「上一個一般模式」做的規則**（已依此更新「已決定的事」）：
  - 上一個一般模式 = 最近一次所在、而且不是目前模式的一般模式。處於潛行模式時就是復原模式；處於一般模式時是在它之前所在的一般模式，中間經過的潛行模式不算。例如「遊玩 → 省電 → 潛行 → 省電」後，回到上個配置是「遊玩」。
  - 所以上一個一般模式不會是潛行模式，「改用復原模式」那條規則用不到。
  - cfg 的 `[General] PreviousMode` 記「復原模式之前的一般模式」：復原模式換成另一個一般模式時，原本的復原模式記到這裡。實際目標在切換時由它與復原模式算出（`AppConfig.PreviousNormalMode`）。
  - 不存在（還沒切換過、被刪除）時用順序第一個一般模式；那就是目前模式時這條切換條件不切換，避免一直重新套用同一個模式。
- **cfg**：`To=Previous`；`To=-1` 不會被當成它（目標模式不存在，讀取時略過）。
- **介面**：目標模式下拉選單的第一個選項，儲存格提示與表格下方都寫出意思。目標模式欄加寬，條件欄縮窄（截圖確認「回到上個配置」與「鍵盤滑鼠」都放得下）。
- **預設值**：新增與複製潛行模式時，內建切換條件的目標都是「回到上個配置」（複製時不再沿用原本的目標）。
