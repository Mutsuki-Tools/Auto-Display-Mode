# 04: 分層復原（結束、關機登出、守護程式）

**What to build:** 依 ADR-0006，處於潛行模式時，不論怎麼離開都要當下切回復原模式（使用者故事 24～27）。程式自行結束，以及收到工作階段即將結束的通知時，先套用復原模式。進入潛行模式時啟動守護程式；主程式閃退、被強制結束或心跳逾時，就由守護程式套用復原模式。斷電後的啟動復原、虛擬螢幕意外消失的處理，已在票 03 完成。

**Blocked by:** 03

**Status:** ready-for-agent

- [ ] 從右鍵選單結束程式時，若處於潛行模式，先套用復原模式（等它完成）再結束
- [ ] 收到 `WM_QUERYENDSESSION`／`WM_ENDSESSION`（關機、登出、重開機）時，若處於潛行模式，先套用復原模式
- [ ] 守護程式：建議用同一個 exe 加參數啟動，不放進主程式的 job object；進入潛行模式時啟動，經由切換離開潛行模式時結束
- [ ] 守護程式監看主程式的存活與心跳；主程式不是正常結束或心跳逾時（數秒），就讀取 cfg、移除虛擬螢幕（若還在）、套用復原模式、更新 cfg 的目前模式，然後結束
- [ ] 守護程式移除虛擬螢幕後，先等 Windows 自己的還原結束（票 02 實測約 0.4 秒；可以等螢幕配置不再變化）再套用復原模式，避免和 Windows 同時改配置
- [ ] 主程式正常結束時通知守護程式，不會重複套用
- [ ] 守護程式套用後，主程式若從卡住中恢復，不會又切回潛行模式（依票 03「虛擬螢幕意外消失」的處理，以及 cfg 的目前模式）
- [ ] 只能有一個守護程式；主程式重新啟動時，若守護程式還在，要能正確接手或結束它
- [ ] 測試：核心中能測的部分（例如結束前的復原、守護程式的決策邏輯，若有抽出）
- [ ] 手動實測：用工作管理員結束主程式、讓主程式卡住（例如以除錯器暫停）、登出、重開機，每種都在幾秒內回到復原模式；結束守護程式本身時，由驅動的心跳保險與 Windows 接手
- [ ] 手動實測要包括平常使用的多螢幕一般模式：主程式與守護程式都被強制結束後，記錄 Windows 自己還原成什麼樣子（票 02 只驗證過單螢幕）
- [ ] 切換條件的目標模式可以選「復原模式」（最後一個處於過的一般模式），不必指定固定的模式；內建切換條件也可以選（見 Comments）
  - [ ] 切換條件分頁的目標模式下拉選單多一個「復原模式」（排在模式之前），只在來源模式是潛行模式時可選；意思寫在儲存格的提示與說明中
  - [ ] 切換時才決定實際的目標：復原模式不存在時用順序第一個一般模式（與 `AppConfig.RestoreTarget()` 相同），規劃被拒絕時開啟所有接上的螢幕
  - [ ] cfg：`To=Restore`；讀取時驗證，來源不是潛行模式時改成順序第一個一般模式並提示；註解說明
  - [ ] 重新編號、刪除模式都不影響它（不指向特定的模式編號）
  - [ ] 狀態摘要、說明與右鍵選單的說明寫出「→ 復原模式」；GLOSSARY 的「目標模式」「復原模式」補上這個用法
  - [ ] 測試：選復原模式的切換條件切到最後一個一般模式、復原模式被刪除時的備案、cfg round-trip 與驗證、來源是一般模式時不能選

## Comments

### 2026-11-22 依票 02 的實測結果修改

- 票 02 驗證了 ADR-0006 的第 3 層（單螢幕）：只剩虛擬螢幕時強制結束測試工具，3.4 秒後驅動的心跳保險移除虛擬螢幕，再過約 0.4 秒，Windows 就以它記住的「只有實體螢幕」配置點亮螢幕，沒有黑畫面、不必按 Win+P。詳見票 02 的 Answer。
- Windows 還原的是實體螢幕單獨接著時最後存下的配置（現有程式套用時用 `SDC_SAVE_TO_DATABASE`），通常就是復原模式。守護程式仍然需要：多螢幕的情況沒有驗證，而且要更新 cfg 的目前模式。
- 依此新增兩項：
  - 守護程式移除虛擬螢幕後，等 Windows 自己還原完，再套用復原模式。
  - 手動實測包括多螢幕的一般模式。
- ADR-0006 與這次結果一致，不必修改。

### 2026-11-22 票 03 完成後的交接與新增項目

#### 票 03 留下的、與本票有關的事

- **心跳不只從介面執行緒送。** 票 03 實測：SetDisplayConfig 開關實體螢幕時，介面執行緒會卡住 2.5～2.8 秒，超過驅動的 3 秒逾時。
  - 所以 `SudoVdaVirtualDisplay` 有心跳執行緒，每 0.5 秒補送，但只在介面執行緒 5 秒內呼叫過 `Ping` 時才補。介面卡死時最多約 8 秒虛擬螢幕才消失。
  - 守護程式判斷「心跳逾時」時，也要容許介面短暫卡住幾秒。
- 離開潛行模式的順序：
  1. 依一般模式開啟螢幕（虛擬螢幕還在）。
  2. 移除虛擬螢幕。
  3. 等 1.5 秒（`AppCoordinator.SettleMs`）。
  4. 重新套用一次。

  守護程式可以沿用。
- 協調者的 `Start()` 已經會：
  - 移除上次留下的虛擬螢幕。
  - 目前模式是潛行模式時，改套用復原模式。
- `TrayApp.ExitApp` 目前只停止心跳，還沒先切回復原模式（本票第一項）。
- 「調整桌面大小以符合」：票 03 手動實測時用手機連線沒有任何改變，使用者決定不需要。程式本來就沒有配合它的處理，本票不必移除任何東西；虛擬螢幕的解析度與更新率照模式的靜態設定。

#### 新增：目標模式可以選「復原模式」（使用者提出）

- 使用者想要「前一個非潛行模式」這樣的目標。GLOSSARY 的「復原模式」就是「最後一個處於過的一般模式」，所以直接用這個名詞，避免另造新詞。下拉選單只寫「復原模式」（使用者覺得加上說明太長），意思放在儲存格的提示（「最後一個處於過的一般模式」）與說明中。
- 只在來源模式是潛行模式時有意義：每次切換到一般模式，它就成為復原模式。來源是一般模式時，復原模式就是來源模式自己，切換條件永遠不會切到別處，所以不能選。
- 實際的目標在切換時決定，與程式啟動時、虛擬螢幕意外消失時切回復原模式的規則相同：
  - 復原模式不存在時，用順序第一個一般模式。
  - 規劃被拒絕時，開啟所有接上的螢幕。
- cfg 寫成 `To=Restore`，不是模式編號，所以重新編號與刪除模式都不影響它。內建切換條件的「目標失效時改成第一個一般模式」也不會發生在它身上。
- 待使用者決定：新建潛行模式時，內建切換條件的預設目標要不要改成「復原模式」。目前是順序第一個一般模式（使用者故事 15）。
